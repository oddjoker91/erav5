Session 14: the MoE scripts, explained

The same ~20M GPT is trained twice with ZeRO-3: once dense and once with every feed-forward layer replaced by a 4-expert, top-2 Mixture-of-Experts. Each section below shows the idea on the left and the code that does it on the right.

★The logic, in plain words

Read this first. The numbered sections below go into the detail of each step.

The idea

A dense block sends every token through the same feed-forward layer. An MoE block has 4 feed-forward layers (experts) and a tiny router. For each token, the router picks the 2 experts that suit it best and blends their outputs. Different tokens use different experts, so each expert can specialise.

What MoE.forward does, in 5 steps

1
Score. The router (Linear 384→4 + softmax) gives each token a probability for each expert.
"cat" → E0 0.50 · E1 0.10 · E2 0.30 · E3 0.10
2
Pick. topk(2) keeps the 2 best experts per token.
"cat" → E0 and E2
3
Rescale. Divide the 2 probabilities by their sum so they add up to 1.
0.50, 0.30 → 0.625, 0.375
4
Run and blend. Loop over the 4 experts. Each one gathers every token that picked it, runs once on that batch, and adds weight × output back into those tokens' rows.
out["cat"] = 0.625·E0("cat") + 0.375·E2("cat")
5
Measure balance. Count each expert's share of the picks (f) and its average router probability (P). Then aux = 4·Σ f·P, which is 1.0 when perfectly even and higher when one expert hogs the tokens.

The block then does x = x + out, the same residual add as the dense model.

How it learns

  • Experts learn like any FFN, but each one only gets gradients from the tokens routed to it. That's what makes them specialise.
  • The router can't learn from the choice itself, since topk returns an index and has no gradient. It learns through the blend weights from step 3, which come from its probabilities. The loss tells it "a bit more E0 would have helped this token", so E0's score for similar tokens goes up.

Why the balancing loss exists

That learning reinforces itself: an expert that's slightly better gets more tokens, which makes it better still, which gets it more tokens. Left alone, one expert takes everything and the others die. Adding 0.01 × aux to the loss pushes the router's probability away from busy experts and toward idle ones, which keeps all 4 in use.

What the training script adds

moe_launch.py is the dense launcher with 3 real changes:

  1. build MoEGPT instead of GPT
  2. shard each MoEBlock with ZeRO-3 instead of each Block
  3. backward on loss + 0.01 × aux instead of loss

Everything else (data, batch, steps, LR, seed) is the same, so the dense vs MoE loss curves differ only because of the architecture.

Want it with numbers? Section 4 traces 4 tokens through every step by hand, and section 2 lets you play with the router.

1Only the feed-forward layer changes

Attention, norms, embeddings and the output head are the same classes in both models.

Each of the 4 experts is a full SwiGLU, the same class the dense model uses. The router looks at each token, picks its 2 best experts, and mixes their outputs with weights that add up to 1.

The dashed experts aren't used by this token. Other tokens in the batch can pick them, so every expert does some work on every step.

transformer.py · Blockdense
class Block(nn.Module):
    def __init__(self, c):
        super().__init__()
        self.c = c
        self.attn = Attention(c)
        self.n1 = RMSNorm(c.D)
        self.n2 = RMSNorm(c.D)
        self.ffn = SwiGLU(c)            # ← 1 FFN
    def forward(self,x,mask):
        x = x + self.attn(self.n1(x), mask)
        x = x + self.ffn(self.n2(x))
        return x

Things to try

  • With the slider at 0, each expert gets about a quarter of the 16 slots (8 tokens × 2 picks), and the balancing loss sits near 1.0.
  • Slide to 4: nearly every token puts E0 in its top 2. E0's load goes toward 2× an even share and the loss climbs toward 2. That higher loss is what pushes the router back toward balance during training.
  • Each token's two weights always add up to 1. For a given token, the MoE output is a weighted average of 2 expert outputs.

Why ~8,192 tokens per expert? 16,384 tokens × 2 picks = 32,768 slots, split over 4 experts. Each expert does half the work of the dense FFN, but 2 experts run per token, so FFN compute per token is about 2× the dense model's. That's why the batch is 64, not 120.
Why call an expert that got 0 tokens (line 47)? Under ZeRO-3, FSDP expects a gradient for every parameter in the block on every GPU. Running the expert on an empty tensor keeps it in the backward pass, so it gets a zero gradient instead of no gradient.
moe_pipeline.py · MoEL21–56
class MoE(nn.Module):
    """Top-k routed SwiGLU experts (dropless: no token is ever dropped)."""

    def __init__(self, c, E=4, k=2):
        super().__init__()
        self.E, self.k = E, k
        self.router = nn.Linear(c.D, E, bias=False)
        self.experts = nn.ModuleList([SwiGLU(c) for _ in range(E)])
        # filled every forward; read by the training loop
        self.aux = None        # load-balancing loss (scalar tensor)
        self.load = None       # fraction of routed slots per expert, shape (E,)

    def forward(self, x):
        B, T, D = x.shape
        xf = x.reshape(-1, D)                                   # (N,D), N=B*T
        # router in fp32 -> probabilities over experts
        probs = self.router(xf).float().softmax(-1)             # (N,E)
        topw, topi = probs.topk(self.k, dim=-1)                 # (N,k) each
        topw = topw / topw.sum(-1, keepdim=True)                # renormalise -> sums to 1

        out = torch.zeros_like(xf)
        for e, expert in enumerate(self.experts):
            # which (token, slot) pairs chose expert e
            tok, slot = (topi == e).nonzero(as_tuple=True)
            # ALWAYS call the expert, even with 0 tokens: keeps every expert in the
            # autograd graph so FSDP gets a (zero) grad for it on every rank
            y = expert(xf[tok])                                 # (n_e,D)
            out.index_add_(0, tok, y * topw[tok, slot, None].to(y.dtype))

        # Switch-style load balancing: E * sum_e f_e * P_e  (=1 when perfectly uniform)
        # f_e = share of routed slots that went to e (no grad), P_e = mean router prob
        f = F.one_hot(topi, self.E).float().sum((0, 1)) / (xf.size(0) * self.k)
        P = probs.mean(0)
        self.aux = self.E * (f * P).sum()
        self.load = f.detach()
        return out.view(B, T, D)

slot says whether the expert was the token's 1st or 2nd choice, which picks the right weight. Each expert runs once on all its tokens together (gather), and the results are added back into those token rows (scatter). After the loop, every token has exactly 2 contributions:

out[t0] = 0.625·E0(x0) + 0.375·E2(x0)

Looping over 16,384 tokens one at a time would be very slow on a GPU. Looping over 4 experts means 4 large matrix multiplies.

aux = 4 × (0.131 + 0.069 + 0.0625 + 0.016) = 1.11, a bit above the balanced minimum of 1.0. The gradient with respect to each Pe is 4·fe. E0 is the busiest, so its probability is pushed down hardest, which frees up share for E3.

How the router learns

The choice (topi) is just an index, so no gradient flows through it. The weights (topw) are computed from probs, so they do carry a gradient.

When the language-model loss backpropagates, it asks for each token: "would a bit more E0 and a bit less E2 have helped?" That signal flows topw → probs → router.weight. The router gradually raises the scores of experts that help a token.

Why experts specialise: an expert only gets gradients from the tokens routed to it. If E1 keeps getting verb-like tokens, it trains mostly on verbs and gets better at them. The router then sends it more verbs, and the effect reinforces itself.
Why the balancing loss is needed: the same feedback can run away. If E0 gets slightly better early on, it gets more tokens, so more training, and so even more tokens, until E3 gets none (a dead expert). The balancing loss, at weight 0.01, keeps nudging the shares back toward even.

5The load-balancing loss

Without it, the router tends to settle on 1–2 favourite experts, and the other experts stop learning.

aux = E · Σe fe · Pe

MeaningGradient?
feshare of the top-2 picks that went to expert e (counted from topi)no, it's a count
Peaverage router probability for expert e over all tokensyes, flows to the router

Pushing aux down moves probability away from overloaded experts (high fe) and toward idle ones. It's weighted 0.01, small enough that it nudges routing without fighting the language-model loss.

The model computes this per layer. aux_loss(model) averages it over the 7 MoE layers from the last forward pass.

moe_pipeline.py · stats + helpersL50–55, L96–108
# inside MoE.forward
f = F.one_hot(topi, self.E).float().sum((0, 1)) / (xf.size(0) * self.k)
P = probs.mean(0)
self.aux = self.E * (f * P).sum()
self.load = f.detach()

def moe_layers(model):
    return [m for m in model.modules() if isinstance(m, MoE)]

def aux_loss(model):
    """Mean load-balancing loss over all MoE layers of the last forward."""
    layers = moe_layers(model)
    return sum(m.aux for m in layers) / len(layers)

def expert_load(model):
    """(L,E) tensor: per-layer share of routed slots each expert got."""
    return torch.stack([m.load for m in moe_layers(model)])

moe_pipeline.py · param_countsL111–116
def param_counts(model, E, k):
    """(total, active-per-token) parameter counts for an MoEGPT."""
    total = sum(p.numel() for p in model.parameters())
    expert = sum(p.numel() for m in moe_layers(model) for p in m.experts.parameters())
    active = total - expert + expert * k // E
    return total, active

8One training step under ZeRO-3

Each GPU keeps half of every block. FSDP gathers a full block just before it runs and frees it right after.

1
Get a batch of 64 × 256 tokens (different tokens on each GPU) and build the masks.
2
Forward, per MoEBlock: FSDP all-gathers the block's full weights (attention + router + 4 experts ≈ 7.7M params ≈ 31 MB), runs it, and frees the gathered copy.
3
MOE
Inside the block, the router splits tokens across experts, and each expert's SwiGLU runs on its ~8k tokens. Each layer stores its aux and load.
4
Cross-entropy loss on the next token.
5
MOE
loss + 0.01 × aux_loss(model)
6
Backward: gather each block again, compute gradients, then reduce-scatter them so each GPU keeps only its half.
7
Clip gradients to 1.0 globally, then AdamW updates this GPU's half of the weights.

Per GPU, model state is ~57M params × 16 bytes (fp32 weights, grads, Adam m and v) ÷ 2 GPUs ≈ 455 MB. Activations still take up most of the peak memory, just as in session 13.

9Reading the MoE logs

Every 50 steps the MoE run adds three columns. Here's how to tell a healthy router from a broken one.

ColumnWhat it isHealthyTrouble
aux_lossbalancing loss, averaged over layers and GPUs≈ 1.0–1.1creeping toward 2+
load_maxbusiest expert's share, as a multiple of an even split (any layer)≲ 1.5≈ 2 (in top-2 of nearly every token)
load_minidlest expert's share, as a multiple of an even split (any layer)≳ 0.5≈ 0 (dead expert)

With top-2 of 4, an expert can get at most half of all slots (2× an even share), because a token can't pick the same expert twice. So load_max tops out at 2.0.
